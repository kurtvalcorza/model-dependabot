### How Dependabot itself decides an alert is raised, fixed or withdrawn

- **Raised:** Dependabot scans the default branch and alerts when "a new vulnerability is added to the GitHub Advisory Database" or when "your dependency graph changes" (for example, after pushed commits). "Only advisories reviewed by GitHub trigger alerts." Detection accuracy depends on keeping manifests and lock files current. Archived repositories are not scanned. GitHub Actions alerts cover semver-referenced actions only, not SHA-pinned ones. Source: https://docs.github.com/en/code-security/concepts/supply-chain-security/dependabot-alerts (fetched).
- **Alert states:** `open`, `dismissed`, `fixed`, `auto_dismissed`. Alerts carry `fixed_at` and `auto_dismissed_at`. `dismissed_reason` is one of `fix_started`, `inaccurate`, `no_bandwidth`, `not_used`, `tolerable_risk`. Source: https://docs.github.com/en/rest/dependabot/alerts (fetched). "Closed alerts that have already been fixed cannot be reopened" (view-dependabot-alerts how-to).
- **Fixed:** The fetched docs **do not state the exact rule** for when an alert moves to `fixed`. The widely understood behaviour is that the alert closes as `fixed` once the dependency graph on the default branch no longer contains an affected version, either because the package was upgraded to a version outside the vulnerable range or because it was removed. That rule is **unverified** against a primary source in this pass. A model-level service should copy the principle: an alert is fixed when re-resolving the dependency set no longer matches the advisory's affected range, never because someone clicked a button.
- **Withdrawn:** GitHub changelog, **2026-10-13**: Dependabot withdraws and removes an alert when the underlying advisory is no longer valid. The `dependabot_alert` webhook gained a **`withdrawn` action**, whose payload includes the alert number, GHSA and CVE IDs, package and manifest path. The REST API now returns **HTTP 410 Gone** for withdrawn alerts, in place of 404. Live on github.com; coming to GHES 3.24. Source: https://github.blog/changelog/2026-10-13-improved-detection-for-withdrawn-dependabot-alerts
- **Design takeaway:** the lifecycle is open, then fixed (by re-evaluation), dismissed (by a human, with a reason), auto-dismissed (by policy), or withdrawn (upstream retracted). This maps cleanly onto model dependencies: "fixed" means the base model or dataset was re-pinned; "withdrawn" means the upstream notice was retracted.

## 2. Weight files: unsafe serialization

Point-in-time scanners are mature. Hugging Face also exposes per-repo scan results as JSON (see below), but **no feed pushes a notice when a scanner's verdict on an already-published file changes**. ## 4. Training datasets

The **scholarly side has real feeds**: Crossref and Retraction Watch for retractions, the DataCite relation graph for new versions and obsoletion, and the Zenodo deleted-records dump for takedowns. The **Hugging Face side has only the webhooks and polling primitives from section 3** (the same API covers `datasets/` repos). No feed keyed to a dataset ID announces that a training set was retracted, withdrawn or relicensed.

## 5. Known model-level weaknesses (incident and vulnerability databases)

**None of these is keyed to a resolvable model identifier** (such as a Hugging Face repo ID plus revision, or a purl). AVID comes closest: it has machine-readable JSON with an `affects.artifacts[]` list, but artifact names are free text. ATLAS and OWASP are taxonomies of technique and risk classes, not per-model advisories.

## Gaps (the opportunity)

1. **Base models: no alert feed exists.** Hugging Face provides primitives (webhooks, `expand[]` model info, commits, `baseModels`), but they are pull or per-repo push. There is no subscribable advisory stream saying that upstream X changed licence, was gated, was disabled, was deleted, or gained a `new_version`. Gating and licence changes have no dedicated webhook event. Anonymous polling cannot tell deleted from private (both return 401). The Kestra blueprint shows the polling pattern but does not walk lineage.
2. **Training datasets: no ML-keyed feed.** Scholarly feeds exist (Crossref `update-type:retraction`, the Retraction Watch CSV, the Zenodo `records-deleted.csv.gz`, DataCite `IsObsoletedBy` / `IsNewVersionOf`, and DataCite DOIs disappearing from the public API when hidden). None is joined to model identifiers, and HF dataset repos have no takedown or retraction notice channel.
3. **Model-level weaknesses: no feed keyed to model IDs.** AVID is machine-readable, but its `artifacts[].name` values are free text ("ChatGPT"), its 2026 volume appears to be bulk-imported general CVEs, and it has no `pkg:huggingface` keys. ATLAS and OWASP are taxonomies. AIID is a weekly snapshot of incidents, not advisories.
4. **No OSV ecosystem for models.** OSV schema 1.9.2 has no ML or Hugging Face ecosystem, although a `pkg:huggingface/<ns>/<name>@<commit>` purl type already exists. Defining one (an OSV ecosystem, or OSV-shaped records keyed by that purl) would let existing OSV tooling consume model advisories. This is the clearest standards-level opening.
5. **Weight-scan verdict changes are not pushed.** Scan results exist (undocumented `securityRepoStatus`) but no event fires when a file's status flips, so a pinned revision must be re-polled or re-scanned.
6. **AIBOM to alert link is missing.** CycloneDX 1.7 and SPDX 3.0.1 can express `trainedOn` / `ancestorOf` / `pedigree.ancestors` / `modelParameters.datasets`, but no tool found reads an AIBOM and resolves those edges against live upstream state the way Dependabot resolves a lockfile against GHSA.
7. Runtime libraries are **not** a gap. OSV, GHSA and PyPI are mature, with withdrawn semantics and change lists (`modified_id.csv`, `withdrawn_at`, and the Dependabot `withdrawn` webhook action as of 2026-10-13).

## Open questions

- Will Hugging Face document `securityStatus` / `/api/models/{repo}/scan` and the `expand[]` fields as a stable API? Do gating or licence changes emit any webhook event at all (only `private` is documented in `updatedConfig`)?
- Can an authenticated poller reliably tell deleted from private from renamed/moved? Do moved repos redirect at the API level? (Not tested.)
- Would the OSV maintainers accept a Hugging Face ecosystem, and what does "version" mean for it: a commit SHA (per the purl type), which would force `GIT`-type ranges?
- What is the exact Dependabot rule for moving an alert to `fixed`? (Not found in the fetched docs; the widely understood behaviour is unverified.)
- Who would author model-level advisories? AVID has the schema but sparse model-specific records; the HF security team and scanner partners have the data but no public feed.
- What are the licence and terms for redistributing AIID snapshots, the Retraction Watch CSV and AVID-imported CVE content inside an alert service?
- Do Endor Labs, Snyk, JFrog Xray, Sonatype or Prisma AIRS already offer base-model or dataset change alerts? Their primary docs were not reached in this pass.
- Unverified secondary claim from the search: a Transformers RCE via crafted `config.json` (reported as CVE-2026-4372, versions 4.56.0–5.2.x with the `kernels` package). Check against NVD or GHSA before citing; if real, it shows that library and weight/config-file risks overlap.
