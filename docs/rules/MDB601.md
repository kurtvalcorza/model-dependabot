# MDB601: A registered parent's finding reaches this model

Watch kind `lineage_inherited`, family lineage. It is a watch event, not an alert: it never opens an
alert on this model and never counts for `check --fail-on`.

Related watch kinds: `lineage_inherited`

## What raises it

This model's manifest names a registered model as a parent (`[[parents]]` with `model` and
`version`), and that parent version has an open alert, or one fixed only by a later version of the
parent, on an item the parent version's own inventory holds. A check then records one
`lineage_inherited` event per parent alert on this model's current version.

What travelled: the event names the parent alert (its id, kind, cause key, severity and state) and
links the parent alert's evidence. From which parent version: the one the edge names, whatever
version the parent has reached since; a child pinned to version 1 still sees a finding that
version 2 fixed. Along which path: every edge from this model up to the parent, with its type and
origin. One edge is `direct`; two or more are `transitive`. An `unspecified` edge on the path is
marked `[relationship unspecified]`. Only edges your own manifest or registration record declared
carry findings; an edge read from an imported inventory carries none.

Which kinds travel along which edge type (a kind not listed travels on none):

| Parent alert kind | fine-tuned-from | adapter-for | merged-from | quantized-from |
| :-- | :-- | :-- | :-- | :-- |
| `package_advisory` | no | no | no | no |
| `weight_file_scan`, `hub_scan`, `format_policy`, `globals_policy` | no | yes | no | no |
| `dataset_retracted`, `paper_retracted`, `dataset_removed`, `dataset_not_findable` | yes | yes | yes | yes |
| `licence_changed` | yes | yes | yes | yes |
| `base_model_disabled`, `base_model_unavailable` | yes | yes | yes | yes |

A finding reaches this model when at least one path passes it on every edge. An `unspecified` edge
passes only the rows that are yes for every type, and a parent named twice under two types passes
only what both types pass. Watch events of the parent never travel.

## What it does not prove

It says the parent's alert applies to an item the parent version you named holds, and that the edge types let it travel. It does not say that this model loads that item: the travel table is a rule of thumb per edge type, not a reading of your bytes.

## How it closes

It is not an alert and does not close: a check stops recording it once the parent alert no longer travels to this model (the parent's alert is dismissed, cleared, withdrawn or fixed by the version you name or an earlier one, the edge is removed or its type no longer lets the kind travel). The parent's owner acts on the parent's alert.

## How to fix or accept it

Read the parent's alert and decide with the parent's owner. To stop it here, register a version of this model that names another parent version or another parent, or no longer names that parent. Nothing on this model needs dismissing: the event never counts for `--fail-on`.

Review steps:

1. Read the inherited event, its path and the parent alert it cites: `model-dependabot alerts <model_id>`.
2. Read the parent's alert with its evidence, using the parent alert id the event names: `model-dependabot alert show <alert_id>`.
3. If this model should no longer name that parent version, register a version that names another: `model-dependabot register MANIFEST.toml --model-id <model_id>`.
