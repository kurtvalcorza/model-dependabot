# Decisions on RFC #5 and RFC #6

**Date**: 2026-11-04
**Decided by**: the project owner
**Baseline**: `main` at `7adfa4590552cc864a2cb16aacbf7f599a29e6ef`
**Covers**: #5 (evidence-backed dependency discovery and inventory assurance) and #6 (model
supply-chain assurance roadmap)

These are direction decisions. They do not approve an implementation: each phase is still specified
with Spec Kit (specification, plan, tasks) before it is built, as the constitution requires.

## D1. Roadmap tracking (#6, decision point 1)

The four-phase direction in #6 is accepted. Phases 2, 3 and 4 are split into their own issues now
(#7, #8 and #9), so each gets its own specification and pull requests. #6 stays open as the roadmap that links them.

## D2. Phase 1 shape (#5, #6 decision point 2)

Phase 1 is a standalone, read-only pair of commands: `discover` (propose candidate dependencies with
their evidence) and `inventory audit` (report findings, inventory assurance and check coverage
separately). Neither command changes an existing manifest or inventory. A proposed manifest or BOM is
written only to a path the user names explicitly. Command names stay provisional until the CLI
contract is reviewed.

## D3. First user of actionable alerts (#6, decision point 3)

The first version of the phase 2 advisory view is designed for the **model maintainer**: which
inventory entry is affected, how it relates to the model, what is established and what is inferred,
and which review steps come next. Security-reviewer and release-engineer views can follow.

## D4. Release gate timing (#6, decision point 4)

The phase 3 `gate` command is out of scope until #5's trust rules are settled and SEC-01 is fixed. It
is always opt-in. `check` keeps its current exit behaviour: findings alone never make it fail.

## D5. First lineage relationship types (#6, decision point 5)

The first manifest schema extension for multi-parent lineage supports all four proposed types:
`fine-tuned-from`, `adapter-for`, `merged-from` and `quantized-from`. Existing single `[base_model]`
manifests keep working unchanged.

## D6. Trust of imported code-free claims (#5, SEC-01)

A third-party BOM's claim that a weight file cannot run code is a claim, not a measurement. Before it
counts under the strict format policy it is checked against the file's bytes, or against pinned
authoritative metadata, when either is available. Otherwise the entry is marked **unverified**. An
unverified code-free claim can never suppress an alert, never stand in for the deployed artifact as a
code-free sibling and never satisfy a future release gate.

## D7. Hardening tasks (#5, SEC-02 to SEC-04)

SEC-02 (redirect destinations), SEC-03 (unbounded response reads) and SEC-04 (redaction of malformed
bodies before the ETag cache stores them) do not depend on the design decisions above. Each gets its
own issue (#10, #11 and #12) and its own small pull request, starting now.

## D8. Where decisions are recorded

In this file and in a summary comment on #5 and #6.
